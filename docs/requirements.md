**计分：每币平均彩票，不是累加分。** 基准 **45/8 = 5.625** 张/币。

| 概念 | 公式 |
|---|---|
| 每币平均 | `彩票 ÷ 已用币` |
| 本局成绩 | 每币平均，保留三位小数 |
| 量化分 | 复用 `core/quantize.js`：达到 5.625 得 100，超出按对数，不足按线性 |

**为什么是"每币"而不是"总彩票"**：推币机是吃币的机器，投得多总分自然高——
比谁币多没有意义。每币能换回多少票才是这台机器的回报率，才是水平。

**为什么基准是 45/8**：实测自动连发不瞄准稳定在 **5.3 张**，瞄准彩票槽 **5.73 张**。
5.625 卡在两者之间——不瞄准约 94 分，瞄准到位刚过 100。
也就是"必须瞄准才够 100"，挂机刷不到满分。
盘面是越推越顺的：前 20 秒每币只有 1.18 张，2 分钟才 4.5 张。

**上游更新不会覆盖本地改动。** 上游会持续发新版本（已从 v1.2.5 跟到 v1.2.7），
而本移植有多处与上游有意不同（大龙珠尺寸、质量、初速、非法灯组保护）。
`docs/donghai-fork.md` 逐条记着这些差异和理由，
`tools/check-donghai-fork.mjs` 把它们钉成 21 条断言，跑测试时自动校验。
覆盖了就会红——不会静默丢失。

**结算**：机台里有「结算」按钮，随时可点，按当前数据当场算分。
点「再来一局」清空盘面重开——不清的话上一局攒的龙珠和灯会带到下一局，
等于用别人的钱打自己的榜。

**每日挑战**：每天从 50 / 80 / 100 / 120 币中随机一档（按日期哈希，所有人算出同一档，
不需要服务器下发）。每人每天 3 次机会，取最好 1 次计入周榜。
币数上限从第一颗珠子就生效——否则玩家先投 200 币把盘面养起来再"发现"限额，
成绩就不可比了。

**周榜**：本周每天当日最好成绩**累加**，每周一零点清零。
不是"取本周最高的一天"——那样玩一天就够了。

**龙珠入盘初速为珍珠的 3 倍**（用户要求）。原 README 写"×3"，但代码是
`3.45 vs 1.35` = 2.56×，现在改成显式的 `DRAGON_SPEED_MUL = 3`。

## 四、BGM

**编码参数：11025Hz / 56kbps 单声道 MP3。** 这两个数是配套定的：

- **采样率**：11025Hz 的奈奎斯特频率是 5512Hz。实测四首曲子的每个声部在
  11kHz 下能量保留 100%~109%（合成器音色谐波有限，5.5kHz 以上本来就没内容），
  所以降采样率没有可听损失，纯粹省体积。
- **码率**：MPEG-2 Layer III 在 11025Hz 下的码率表是
  8/16/24/32/40/48/56/64 kbps，**最高只到 64**。
  传 96 会被 lamejs 静默忽略（实测 64/96/128 三档输出全是 68.5kbps）。
  想真正拿到 96kbps 必须把采样率提到 16000Hz 以上。

> **没有「音频上限 10MB」这回事。** 那是早期写死在 gen-bgm.mjs 打印语句里的
> 字面量，平台没有这条限制，代码里也从来没有校验过。
> 唯一的硬约束是整包 100 MiB，音频只占其中 5.7%。

每款游戏一首，**先生成 MIDI 再转 WAV**，3-5 分钟可循环。

转盘合计 **8+4+5 = 17 个 value**。

**扩容方式：只追加，不移动。** 新增的 value 一律接到编号表末尾
（`save_30..save_40`），原有域的 `start`/`count` 一个都不动。
原因是每个域占哪几个 `save_N` 是写死在 `core/save.js` 里的；
如果为了扩容把后面所有域往后挪，老用户已经写进 `save_18` 的数据
就会被新代码当成别的域来读，直接错位。所以 `SCOPES` 里用
`extra` 字段挂新增的键，`scopeKeys()` 会把 `count` 段和 `extra` 拼起来。

### 存储方式

**连续存储，不按 value 拆分业务**：

- 每个域是一段连续字节流，自动切块写进 `save_N`
- 每块上限 16000 字节（云端限制 16384，留 384 字节余量）
- 第 0 块带头部 `S1|<总字节>|<块数>|<校验>|`，作为提交标记
- **从后往前写**，最后写第 0 块；中途失败不会留下半个存档
- 数据一律先压缩再 base85 编码，输出纯 ASCII，字节数 == 字符数
